# The CSV, and its traps

[&larr; back to the README](../README.md)

Everything here was **measured from a real 6,517-row Strong export**, not assumed. Where the
original build specification disagreed with the file, the file won. This page is why the ingest code
looks the way it does: the shape of the export, the places its structure is ambiguous, and the one
ordering in `src/ingest/classifyRow.ts` that silently loses 81 real sets if it is reversed.

See also [Architecture](architecture.md) for how the parsed model is layered, and
[Analysis decisions](analysis.md) for what is built on top of it.

---

## About the fixtures

Two corpora, and the distinction matters:

- **`fixtures/sample_workouts.csv`** — committed, and what a fresh clone runs against. It is
  **entirely synthetic**, generated by `scripts/make-sample-fixture.mjs` from a fixed seed, so
  regenerating it is byte-reproducible. It is not a random file: it deliberately reproduces every
  quirk documented below — CRLF with no trailing newline, `Ruhezeit` rows (including one with zero
  seconds), `W`/`D` tokens, isometric holds, the trailing-space name, the `(Dumbell)` misspelling,
  empty-bar sets, a >28-day layoff, and a push/pull/legs rotation for the clustering to recover.
  Without those, the tests below would pass while guarding nothing.
- **`fixtures/strong_workouts.csv`** — a real personal export. It is **gitignored and never
  committed**: a Strong export is two years of training history with exact timestamps, which is
  personal health and routine data. The suite in `src/ingest/fixture.test.ts` holds regression locks
  measured from it and **skips automatically when the file is absent**, so a clone reports them as
  skipped rather than failing.

To use your own data, export from Strong and drop the CSV onto the import page — nothing leaves
your browser. To run the real-export regression locks too, save it as
`fixtures/strong_workouts.csv` and adjust the measured constants in that test file to your export.

## The CSV quirks, and why the code looks the way it does

Everything below was **measured from the real 6,517-row export**, not assumed. Where the original
build specification disagreed with the file, the file won. Two of its figures were wrong: it
claimed 3,935 numeric working sets (the real count is **3,930**) and a set-order range of `1-20`
(the real range is **`1-27`**).

### File shape

| Property | Value |
|---|---|
| Encoding | UTF-8, **no BOM** |
| Line endings | CRLF throughout |
| Final byte | **no trailing newline** — the file ends on a bare comma from an empty RPE field |
| Structure | 6,518 lines = 1 header + **6,517 data rows**, 12 fields on every line |
| Delimiter | comma here, but sniffed across `,` `;` `\t` because Strong has shipped all three |
| Headers | German (`Datum, Workout-Name, Dauer, Name der Übung, ...`) |

Header mapping goes through a locale alias table (`src/ingest/headerMap.ts`) with a positional
fallback, so an English export parses with no code change. Unmappable headers throw a
`HeaderMappingError` naming the columns rather than silently mis-parsing.

### `Datum` is a timestamp, not a date

Values look like `2023-01-09 18:15:00`. That is good news: `(Datum, Workout-Name)` is a genuinely
unique workout key (199 distinct workouts here), so two sessions on one day never collide.

It is parsed as **local wall-clock time**. `new Date("2023-01-09")` would be interpreted as UTC and
shift the day backwards west of Greenwich.

### `Reihenfolge festlegen` (Set Order) is a tagged union

| Value | Count | Meaning |
|---|---|---|
| `Ruhezeit` | 2,529 | rest-timer row (39% of the file) |
| `1`–`27` | 3,930 | working set |
| `W` | 53 | warm-up |
| `D` | 5 | drop set |

`Ruhezeit` is localised (`Rest Timer` in English), so classification is **structural first,
strings second**.

> #### The single most dangerous ordering in this codebase
>
> All **81** isometric-hold rows (`Handstand Hold`, `Wall Sit`, `Side Plank`, `Plank`, `deadhang`)
> carry `seconds > 0`, `reps == 0` **and** `weight == 0` — structurally **identical** to a rest row.
> The only thing distinguishing them is their numeric set order.
>
> So in `classifyRow`, **the numeric test must run before the structural rest test.** Reversing them
> silently swallows 81 real sets as rest. `src/ingest/classifyRow.ts` carries a comment saying so and
> `ingest.test.ts` has a dedicated regression test.

The structural test still earns its place: it catches a rest row localised into a language the
token table does not know. And one `Ruhezeit` row has `seconds == 0`, which only the token path
catches — which is why both paths exist.

Anything matching none of these becomes an `unknown` token. Unknown rows are **never silently
dropped**; they surface in the import report with their verbatim value and file line number.

### Rest rows are attributes, not entities

The rest value is only the user's configured timer setting, not measured rest, so it has no
analytical value — but it is attached rather than discarded. Walking rows in order, a rest row
writes `restAfterSec` onto the most recently emitted set and is then dropped. Rest rows never
appear in the sets table or in any set count.

The scoping rule is what keeps this honest: `lastSetIdx` resets to `null` on **both** a workout
change and an exercise change, which makes cross-workout leakage structurally impossible rather
than something to remember. Consecutive rest rows are **last-write-wins** — these are timer
settings, not elapsed intervals, so summing them would be actively wrong. A set with no following
rest row gets `restAfterSec: null`, meaning *unknown*, never `0`.

### Duration

`Dauer` is a human string (`1h 5min`, `54min`, `1h`) repeated identically on every row of a
workout, so it lives on the `Workout`, not the set. All 98 distinct values in this export match
the `h`/`min` grammar; the parser also tolerates `1:05:00`, `45m` and bare numbers.

### Workout names carry no routine information

Values are Strong's auto-generated time-of-day labels (`Abend-Workout` 3,872, `Nachmittags-Workout`
1,520, `Mittags-Workout` 673, `Morgen-Workout` 452). **Do not treat this column as a split or
routine name.** It is only part of the grouping key.

### Columns that are empty in practice

- **RPE** — empty in all 6,517 rows. Parsed, nothing built on it.
- **Workout-Notizen** — 0 non-empty. **Notizen** — 3 (`Ring`, `Hold in min`, `+20 kg`).
- **Entfernung** — 9 non-zero rows.
- **Sekunden** on non-rest rows — 81 rows, the isometric holds above.

### Distance is probably kilometres, not metres — so it is not converted

The spec asserted `Entfernung` is metres. But the `Running` rows read `0.8` and `1.0` against
420 s and 318 s, which is plainly **0.8 km**, not 0.8 m. `Stepper` rows read 25–62, likely floors.

The field is therefore stored as `distanceRaw` with the unit explicitly unknown, excluded from
every metric, and flagged in the import report. Multiplying by 1000 would bake in a 1000× error
across data nobody is analysing anyway.

### Data-quality traps in exercise names

- **`Single Leg Extension `** has a trailing space — the only whitespace-dirty name. Names are
  trimmed for the join key, and both the trim and any resulting **collision** are reported.
- **`(Dumbell)`** is misspelled with one `b` and must normalise to `dumbbell`.
- **`Push Up (Knees)`** proves the trailing parenthetical is *not always equipment*. An
  unrecognised parenthetical is treated as a **variation**, leaving equipment `unknown` for the
  heuristics rather than being forced into a slot.
- Only 67 of 130 names have any parenthetical. The rest are bare, including user-invented ones
  (`deadhang`, `Sally Challange`, `Gylenhall Rotation`, `Kabelzug rear shoulder`).
- 2 `Pull Up` rows carry 40 kg but **`reps == 0`** — abandoned sets. Counted, reported, and
  excluded from volume.

## The critical design constraint: bodyweight

**1,233 of 3,988 working sets (31%) have weight = 0** in the reference export. The most-trained
movement there is `Pull Up`, and roughly two thirds of its sets are logged at bodyweight with the
rest carrying added plates.

Treating weight as absolute load would make a third of this training compute to zero volume and
render the single biggest lift invisible. So every exercise carries a `loadType`, and effective
load resolves per set:

| `loadType` | Effective load |
|---|---|
| `external` | `weightKg` |
| `bodyweight` | `bodyweightAt(date)` |
| `bodyweight-plus` | `bodyweightAt(date) + weightKg` — the weight column is *added* load |
| `assisted` | `max(0, bodyweightAt(date) - weightKg)` — the weight column is *assistance* |
| `duration` | `null` — track seconds, exclude from volume |
| `distance` | `null` |

`bodyweightAt` interpolates linearly between recorded entries and clamps at both ends. With no
entries recorded it returns a configurable fallback and the Settings view shows a first-run
prompt, rather than silently computing zeros.

### Getting bodyweight in

Entries can be typed by hand in Settings, or imported from Strong's **measurements export**
(`src/ingest/parseBodyweightCsv.ts`). That file is the messiest input the app takes -- it is a
long/tall table of every measurement Apple Health ever wrote, so it spans years before training
started, mixes in kinds we do not model, and contains junk. The importer therefore:

- **filters by measurement kind**, so a body-fat row in `%` is reported as a different
  measurement rather than as a broken weight;
- **converts per row** using that row's own unit cell;
- **range-checks** against 30-300 kg, which is what catches the zeros health apps write;
- **clips to `report.dateRange`**, the workout span -- a weight from eight years before the
  first session cannot inform any set, and anchoring the ramp there actively misleads;
- **collapses each day to its last reading**, because the model stores one weight per day;
- **drops values more than 25% from the median**, but only once there are at least three
  readings: below that the median sits between two far-apart values and would cull both.

Every refused row lands in the report with its file line and verbatim value -- the same
"nothing is silently dropped" contract the workout import holds. The result is merged into the
existing entries with the import winning a same-date collision (`mergeBodyweight`).

**It does not densify.** Only real observations are stored; interpolation stays a read-time
concern, so correcting one entry still retroactively fixes all history.

`SetRecord` stores the **raw** weight. Effective load is always derived, never persisted, so
correcting a `loadType` or a bodyweight entry retroactively fixes all history.

### Zero-weight sets on `external` exercises

36 `Squat (Barbell)` sets are logged at weight 0 — deliberate empty-bar movement prep. They are
real sets, so they count in set counts, but they are excluded from volume and e1RM and flagged
`isUnloaded` so later charts can decide. A `null` weight means *missing data* and is kept distinct
from a `0`.
